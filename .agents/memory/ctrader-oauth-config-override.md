---
name: cTrader OAuth breaks silently from config.json overriding secrets
description: Why cTrader OAuth ("Client credentials invalid" / CH_CTID_TRADER_ACCOUNT_NOT_FOUND) can fail even when Replit Secrets look correct, and how account IDs must be resolved.
---

## config.json overriding Replit Secrets is a recurring failure class
If a settings/config UI lets users save fields into a local `config.json` (or similar file) that gets loaded into `os.environ` on startup, and that file ever captured `CTRADER_CLIENT_ID`/`CTRADER_CLIENT_SECRET` (or any other secret-backed field), it silently shadows the real Replit Secret with a stale value forever after — even if the Secret itself is later fixed. Symptom: cTrader's OAuth token exchange returns `{"errorCode":"INVALID_REQUEST","description":"Client credentials invalid"}` even though the Secret is correct, because the ID/secret pair became mismatched (one field overridden, the other not).
**Why:** any per-request `os.environ[key] = val` write from a settings-save endpoint takes precedence over the Secret for the rest of the process lifetime, and a startup loader that reads a JSON file into `os.environ` reintroduces stale values every restart.
**How to apply:** never let CTRADER_CLIENT_ID/CTRADER_CLIENT_SECRET (or other secret-backed fields) round-trip through a plain config file. Explicitly exclude them at both load-time (purge from the file on load) and save-time (strip from the payload before writing), and remove any UI inputs for them — they should be Secrets-only, no override path.
**Debugging tip:** cTrader's `apps/token` endpoint returns *different* error bodies depending on whether the auth *code* is fresh/valid vs the client_id/secret pairing — feeding a deliberately-fake code to the same endpoint and comparing the error (`ACCESS_DENIED` vs `INVALID_REQUEST: Client credentials invalid`) helps distinguish "code problem" from "id/secret mismatch problem" without waiting on a real OAuth round-trip.

## There is no REST endpoint to list cTrader accounts
`https://openapi.ctrader.com/apps/accounts` does not exist (404) — trying to call it as REST for post-OAuth account discovery always fails, and if that failure path is fail-closed with a hardcoded fallback (e.g. always assume `isLive=True` and reuse a manually-configured account ID), the app never surfaces the real error; it just fails later and confusingly (e.g. bot reports "started successfully" but every trading-loop cycle throws `CH_CTID_TRADER_ACCOUNT_NOT_FOUND`).
**How to apply:** account discovery must go over the WebSocket/protobuf JSON gateway using `ProtoOAGetAccountListByAccessTokenReq`/`Res` (payloadType 2149/2150, see `ctrader-json-gateway.md`), tried against both `demo.ctraderapi.com` and `live.ctraderapi.com` since the account's demo/live nature isn't knowable in advance. The response's `ctidTraderAccount[]` entries carry the real `ctidTraderAccountId` *and* a reliable `isLive` field per account — no guessing needed.

## traderLogin vs ctidTraderAccountId, and translating user input
Users naturally know their broker "login number" (`traderLogin`, e.g. a 7-digit number shown in the trading platform) and will type that into any "Account ID" field — but the Open API's `ProtoOAAccountAuthReq` requires the internal `ctidTraderAccountId`, a different, larger number. Silently accepting whatever the user typed causes the same `CH_CTID_TRADER_ACCOUNT_NOT_FOUND` failure.
**How to apply:** whenever a human-entered account identifier is saved (Settings UI, config API), resolve it against the account list (matching by either `ctidTraderAccountId` or `traderLogin`) and persist the translated `ctidTraderAccountId`, not the raw input — do this automatically rather than asking the user to look up the "correct" number themselves.
